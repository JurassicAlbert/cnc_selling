# Production-readiness audit — 2026-08-30

Read-only audit of the whole application before any code changed. Every
finding below was verified by reading the actual file named, not inferred
from a naming convention. Where something could not be verified in this
environment it says so explicitly.

Baseline at audit time: `npm run typecheck` clean, 78 test files
(24 unit, 47 integration, 7 e2e specs).

---

## Part 1 — Findings, by severity

### P0-1 — Unauthenticated privilege escalation via `apply*` Server Actions

**The single most serious finding in this audit.**

Every file in `src/server/actions/` begins with `'use server'`. In the App
Router, **every exported async function in a `'use server'` module is a
publicly reachable HTTP endpoint**, not just the ones a component imports.
Next.js's own docs state this outright: such functions must perform their
own authorization.

This codebase's testability convention is an `applyXxx(actor, …)` /
`xxx(…)` pair: the wrapper calls `requireStaffSession()` and delegates; the
`apply*` half takes the caller's identity **as its first argument** and
performs no session check at all. Both halves are exported from the same
`'use server'` file.

Result: ~80 `apply*` functions are live action endpoints that accept a
forged actor. A request carrying a hand-made
`{ userId, role: 'ADMIN', name, email }` object as argument 1 gets the
privileges of that object. Confirmed present in 28 admin action files plus
four customer-facing ones.

Worst individual cases:

| Function | File | What a forged actor gets |
|---|---|---|
| `applyChangeStaffRole` | `admin-staff.ts:70` | promote any account to `ADMIN` |
| `applyInviteStaffUser` | `admin-staff.ts:35` | create a staff account |
| `applyPublishPricingVersion` | `admin-pricing.ts:122` | change every price on the site |
| `applyMarkOrderPaid` | `admin-orders.ts:119` | mark any order paid |
| `applyOrderStatusTransition` | `admin-orders.ts:29` | drive any order's state machine |
| `applyAnonymizeCustomer` | `admin-customers.ts:30` | destroy customer records |
| `applyUpdateStoreSettings` | `admin-store-settings.ts:31` | rewrite bank details shown to customers |
| `applySubmitAccountReview` | `reviews.ts:93` | post a review as any user id |
| `applyToggleFavoriteDesign` | `design-favorites.ts:19` | write to any user's favourites |
| `applySubmitOrderSupportRequest` | `support-requests.ts:124` | file support requests as another user |

The action id is a build-derived hash rather than the function name, so this
is not trivially exploitable from outside — but that is **obscurity of an
identifier, not an authorization check**, and the ids are stable per build.
`ARCHITECTURE.md` §16.1's own rule ("Every Server Action re-derives the
actor from the session. No id is ever trusted from the request body") is
violated by ~80 endpoints.

**Fix:** move every `apply*` into a plain (non-`'use server'`) module so it
stops being an endpoint. Tests import from there; wrappers import and call
it. Add an automated guard so this cannot regress.

### P0-2 — Double-submitted checkout creates two real orders

`submitCheckout` → `createOrder` (`src/server/orders/create-order.ts`) has
**no idempotency mechanism of any kind**. The flow is: read cart → re-price
→ open transaction → create order → delete the cart rows.

Two concurrent submissions both read a non-empty cart, both re-price
successfully, both create an `Order` with its own `orderNumber` and
`accessToken`. The second `deleteMany` deletes nothing (already gone) and
does not fail. The customer ends with two orders and two confirmation
emails for one purchase.

The checkout form's `useFormStatus()` disables the button while pending,
which covers a plain double-click *in one tab*. It does not cover:

- two tabs with checkout open
- a retried request after a dropped connection
- browser back → resubmit
- a direct POST to the action endpoint

Reachable states: duplicate orders, duplicate order numbers consumed from
the counter, duplicate confirmation emails, and a customer who pays once
for an order the shop believes was placed twice.

**Fix:** an idempotency key minted per checkout render, stored `@unique` on
`Order`; plus claiming the cart rows *inside* the transaction and aborting
if the claim comes up short (covers two independent renders racing).

### P0-3 — Lost update on cart quantity (read-then-write race)

`adjustCartItemQuantity` (`src/server/actions/cart.ts:202`):

```ts
const current = await prisma.cartItem.findUnique(...);   // reads 1
await prisma.cartItem.update({ data: { quantity: clamp(current.quantity + delta) } });
```

Two rapid `+` clicks both read `1` and both write `2`. The customer clicked
twice and got one increment. Symmetrically, a `+` and a `−` racing can leave
either value. This is the classic lost update; nothing here is atomic.

**Fix:** a single atomic statement that clamps in the database, so
concurrent adjustments compose instead of overwriting.

### P1-4 — Repeated "add to cart" of an identical configuration creates duplicate rows

`addToCart` unconditionally creates a new `Configuration` **and** a new
`CartItem` on every call. Clicking "Dodaj do koszyka" twice — or a retried
request — yields two visually identical cart rows the customer must remove
one at a time.

The schema comment on `CartItem` correctly argues that *two different*
configurations must be two rows. That is right and stays. It does not
follow that two *byte-identical* configurations should be two rows, and the
"Duplikuj" button already exists as the explicit way to ask for a second
independent line.

Note this is genuinely distinct from P0-3: quantity and identity are
different concerns.

**Fix:** merge into an existing cart row when every configuration field
matches exactly (product, design, custom design, material, finish,
thickness, width, height, install variant, personalization text, font);
create a new row otherwise. `duplicateCartItem` keeps its current
deep-copy behaviour untouched.

### P1-5 — Cart badge goes stale after every cart mutation

Every cart action calls `revalidatePath('/koszyk')` — page scope only. The
cart badge lives in `SiteHeader`, rendered from `StorefrontChrome`, which
is mounted by the `(shop)`/`(marketing)` **layouts**. Nothing invalidates
the layout, so after adding or removing an item the badge keeps showing the
previous count on any other page until the client Router Cache expires.

Round 10 fixed exactly this for order completion (`create-order.ts:262`)
and the same reasoning applies to all five cart mutations. It was not
carried across.

**Fix:** `revalidatePath('/', 'layout')` in the cart mutations, same as
order creation.

### P1-6 — Staff order mutations are not idempotent

`applyMarkOrderPaid` reads `paymentStatus`, checks it is not `PAID`, then
writes — outside a transaction. Two concurrent clicks both pass the check
and both write, producing two audit-log entries for one state change.
`applyOrderStatusTransition` has the same shape and additionally emits a
duplicate `OrderEvent` and a duplicate customer email.

**Fix:** make the write conditional on the expected current state and treat
"affected 0 rows" as "someone else already did it".

### P1-7 — Order creation re-prices every cart item sequentially

`create-order.ts:125` is a `for … await` loop calling
`priceAndValidateSelections` per item. Each call does its own catalogue
reads. A 5-item cart pays 5 round-trip waterfalls in series while the
customer waits on the submit button. The items are fully independent — this
is the textbook `A → B → C` that should be `A + B + C`.

**Fix:** `Promise.all`, preserving order and the first-mismatch rejection.

---

### P1-8 — Missing rate limits required by the project's own spec

`ARCHITECTURE.md` §16.1 requires rate limits on "uploads per session/hour,
**order creation per IP**, **auth attempts**". Only the upload limiter
exists (`src/server/upload/rate-limit.ts`). Order creation and login are
unthrottled.

Not fixed in this round — flagged, with a note that it needs a real
decision about the limiter's storage (the upload limiter counts DB rows,
which does not transfer cleanly to login attempts).

---

### P2-9 — `STAFF` can write the catalogue, contradicting the documented role matrix

`ARCHITECTURE.md` §16.3 says `STAFF` gets "pricing and catalogue
**read-only**", and §16.2's matrix lists "`STAFF` → catalogue write → 403".
In practice every catalogue mutation uses `requireStaffSession()`, so
`STAFF` can create, edit and retire products, materials, designs, finishes,
categories and collections. Pricing *is* correctly `requireAdminSession()`.

This is a documented-intent vs implementation divergence. It is not
exploitable by a customer, and which side is wrong is a **business
decision** — either the docs overstate the restriction or ~20 actions need
tightening. Not changed unilaterally; raised for the owner.

### P2-11 — Whole pickup-point dataset ships to the browser

`CheckoutForm.tsx` imports `searchPickupPoints`/`findPickupPointById` as
runtime values, so the entire `PICKUP_POINTS` array is bundled into client
JS. Harmless at today's 16 entries; it becomes a real payload problem the
moment this is swapped for a live directory, which is the stated plan
(`docs/OPEN_ITEMS.md` §3). Worth knowing before that swap, not worth
restructuring now.

## Part 3 — What was already right

Worth stating, because the audit brief assumes the worst and much of this
codebase does not deserve it:

- **Order snapshots** are genuinely immutable and complete; renaming or
  retiring a product/pattern later cannot corrupt an existing order.
- **Server-side price authority** is real: `createOrder` re-prices every
  line and rejects on any mismatch. No client total is trusted anywhere.
- **Delivery pricing** is re-evaluated server-side through the exact same
  function the picker used, so the two cannot disagree.
- **Payment honesty** is enforced structurally: `isConnected` gates
  checkout, and an unconnected provider is rejected like a nonexistent one.
- **Order numbers** come from a real Postgres upsert-counter, not
  `count() + 1` — collision-safe under concurrency.
- **Guest tokens** are HMAC-signed; order access tokens are compared in
  constant time; file access 404s rather than 403s.
- **Ownership checks** in cart/configuration/design actions genuinely
  re-derive the owner from the session and never trust a request id.
- **Soft-delete invariant** is real and has its own test.
- The admin panel is a genuinely complete CRUD surface over the model.

tests were not on the audit's own list, and one bug was in the audit's own
fix — recorded here because that is the honest record, not a tidier one.

### Performance

`createOrder` re-priced cart items in a `for … await` loop — N sequential
catalogue round-trips while the customer waits on the submit button, for
work with no inter-item dependencies. Now `Promise.all`, preserving order
and the first-mismatch rejection. This is the only change made purely for
speed; nothing else was "optimised" without a measured or structural reason.

The audit also **declined** an obvious-looking optimisation: converting
`SearchBar` and the rest of the storefront chrome to MUI would have made the
"vanilla UI" finding go away, at the cost of mounting a client theme
provider on every storefront page — which an earlier Lighthouse pass
specifically removed for LCP. Left as-is, with the reason written into the
file so the next reader doesn't "fix" it.

### Not verified, and why

- **Every payment-callback scenario in the brief** (duplicate callback,
  delayed callback, browser closed before callback, payment succeeded but
  order creation failed). No provider is connected — `docs/OPEN_ITEMS.md`
  §1. There is no handler to test.
- **Real carrier tracking behaviour.** No carrier API is connected; the
  shipment record is manually managed by staff, honestly.
- **Load and real-device performance.** No profiling was run: the
  performance findings here are structural (a sequential loop, a bundled
  dataset), not measured. Anything requiring before/after numbers is
  flagged as such rather than claimed.
